01 — Introduction

Every good infrastructure project I've ever built started as a personal problem, not a résumé line. This one started with a group chat at 11pm.

Minecraft is the game my friends and I keep coming back to. Not because it's the best game ever made, but because it's the one thing that still gets all of us into the same voice call. We've drifted — different careers, different cities, different time zones, one of us literally stationed overseas. Life pulled everyone in separate directions. And then somebody types "server?" into the chat and suddenly it's like none of that happened. That's the part worth protecting. The game is just the excuse.

The trouble is that the way we'd always done it didn't survive growing up. Boot a server, paste your IP in the chat, play until someone's home internet dies or somebody griefs the world into an accidental anarchy server. Fun, fragile, and completely dependent on one person's laptop staying awake. It worked when we were all in the same dorm. It does not work when "everyone's online" means three continents.

So one night the friend stationed in Qatar dropped a link in the chat: a Hostinger plan built specifically for hosting Minecraft. Everybody pool in, split the cost, problem solved.

It was a completely reasonable suggestion. I clicked through the pricing page anyway.

And honestly? From a normal-person standpoint, it's perfect. One click, enter a card, you're playing in five minutes. No Linux, no config files, no 2am debugging. It just works.

Which is exactly what got under my skin. I'm in school for Computer Information Systems with a cybersecurity focus. I've built infrastructure before. Paying a monthly subscription so a company could run a Java process for me felt like buying bottled water while standing next to a well I knew how to dig. It wasn't about the money. It was about the fact that nobody even thought to ask whether I could just… do this.

So I made them an offer instead of an argument. If I could stand up a setup that matched or beat what Hostinger was selling — same uptime, same "it just works" experience for the people playing — then the friend about to spend a year on Hostinger owed me one year of that subscription instead. Put the money where the trash talk was.

He agreed.

And then it got quiet on my end. Some small part of me was hoping he'd laugh it off. Instead I'd just publicly committed to building production-grade server infrastructure — from scratch, on a budget, on a deadline — for a group of people whose only requirement was "let me punch trees with my friends." No pressure.

What follows is everything that came after that text: Proxmox, LXC containers, Tailscale zero-trust networking, a Velocity proxy, HashiCorp Vault, Prometheus, Grafana, Loki, a self-hosted Gitea CI/CD pipeline, and a custom write-lock failover system I had to invent because the obvious approach corrupts your world. All of it mapped, deliberately, against the DoD's DevSecOps framework. For a Minecraft server. I regret nothing.

The Network Diagram

Here's the whole system on one page. The detail that ties the entire build together is that there are exactly two kinds of people who can touch this network, and they get wildly different doors. I come in as admin over Tailscale and reach everything — Proxmox on 8006, Gitea on 3000, Vault on 8200, Grafana on 3001. My friends come in over the same Tailscale, but their access grant opens exactly one port: 25565, the game. Everything else is invisible to them. Not blocked with a scary error — invisible. And yes, I designed it that way specifically because I know they'll go looking.

The Proxmox host lives in the middle wearing two faces — a local LAN address (192.168.4.41) and a Tailscale address (100.107.12.47). Everything underneath it sits on an isolated internal bridge (vmbr1) at 10.10.10.0/24. Nothing on that subnet is reachable from the outside world. All traffic has to pass through the host first, where iptables PREROUTING rules forward only specific ports from the Tailscale interface to the right container. The home router, the ISP, a stranger on the internet — none of them even know that internal network exists.

Velocity is the single front door for players. Every Minecraft connection hits it on 25565, and it routes the player to a backend PaperMC node. Meanwhile the monitoring stack quietly scrapes metrics from every container and ships every log line to Loki, and Gitea sits off to the side making sure no config change reaches a running service without passing through a pipeline first. That's the whole shape of it. The rest of this post is how each of those boxes got built — and what broke along the way.

Why These Specific Tools

proxmox
Free and open source. LXC containers are lighter than full VMs — each service gets its own isolated environment without the overhead. Proxmox runs on Debian, the same OS as all the LXCs, making the entire stack consistent. VMware costs money.
tailscale
Zero config VPN with built-in ACLs and a free tier that covers this entire use case. No server to maintain unlike WireGuard or OpenVPN. NAT traversal works globally — including Qatar — without touching the home router. WireGuard handles the cryptography underneath.
velocity
More secure and performant than BungeeCord. The modern forwarding protocol cryptographically prevents backend IP spoofing using a shared secret. Velocity is the current community standard for Minecraft proxy infrastructure.
papermc
Fastest Minecraft server implementation available. Better ticks-per-second than vanilla, asynchronous chunk loading, and Spark profiler bundled. The performance ceiling matters when running two nodes on a single desktop machine.
gitea
Self-hosted GitHub equivalent that runs on 512MB RAM. You own the data. Actions runners are built in with no separate CI server needed. The entire dev workflow — push, validate, deploy — runs on the same LXC that hosts the repos.
hashicorp-vault
Industry standard secrets management used in production enterprise environments. No credentials ever touch a config file or repository. Initialized with a single unseal key for homelab simplicity, auto-unsealing on reboot via a dedicated systemd service.
prometheus + grafana
The de facto standard observability stack. Grafana dashboard ID 1860 gives instant Node Exporter visualization across every LXC with zero manual configuration. The same stack used in production at companies running Kubernetes at scale.
loki
Made by the Grafana team so it integrates natively without any plugins or adapters. Significantly lighter than running a full ELK stack on 8GB of RAM. Promtail agents on each LXC ship logs with job labels for filtering by service.
lxc not docker
LXCs are full OS containers with systemd, init systems, and persistent state. Better for long-running services than Docker containers which are designed for ephemeral workloads. Proxmox's clone-from-template workflow is faster and more consistent than Dockerfiles for this use case.

The entire empire runs on an HP EliteDesk 705 G3 Mini — a little corporate desktop I bought off eBay for $70. Some company decommissioned it, wiped the asset tag, and shipped it out still running Windows 10 Pro. The first thing I did was flatten it. Seventy dollars. Less than the friend was about to spend on a single year of Hostinger. That number mattered to me, because the whole argument was that the "expensive convenient option" wasn't actually buying you much.

Hardware Specs HP EliteDesk 705 G3 Mini · AMD APU · 4 cores · 8GB DDR4-2400 · 210GB SSD · ~10–15W idle power draw

The RAM has earned the right to its own paragraph, because it nearly broke me before I'd installed a single service. I started with two mismatched SO-DIMMs I had lying around — an 8GB DDR4-2666 and a 16GB DDR4-3200 — figuring more is more. The EliteDesk disagreed, loudly and silently at the same time. The 16GB stick refused to POST on its own. No beep, no message, just a black screen and me staring into the BIOS like it owed me an explanation. After enough digging I found out the board is validated for DDR4-2400 specifically and is genuinely picky about anything outside its blessed list.

So I built the entire thing on a single 8GB stick while I hunted for a proper match. Which brings us to the most expensive line item in the project — and the most satisfying. After they lost the bet, the group had to chip in and buy me a matching 8GB DDR4-2400 SO-DIMM. Street price: about $15 on eBay.

Fifteen dollars. That was the agreed-upon cost of losing a tech bet to the friend who built a better server than the thing you were about to pay a company for. Apparently that's what dignity goes for these days, and they paid it without much of a fight.

Total hardware cost, RAM included: $85 — once. The Hostinger plan they were ready to buy costs more than that every year. We're not going to dwell on the return on investment here. This was never about ROI. It was about principle, and the principle won.

04 — DevSecOps Methodology

Here's where I made a decision that turned a weekend project into something I'd actually put my name on. Before I touched a single config file, I mapped the whole build to the DoD DevSecOps Fundamentals Guidebook: Tools & Activities (v2.0, March 2021). It's an unclassified, publicly available document that breaks a software lifecycle into eight phases and spells out the security activities expected at each one. It was written for Department of Defense programs, but the framework is honestly just a clean description of how mature software delivery works anywhere.

I did this on purpose. Most homelab writeups end at "I installed it and it worked," and that's fine — but it's a story about a tool, not about an engineer. I wanted to force myself to justify every component against a real, externally-defined standard. If a piece of this build couldn't be tied to an actual phase of a real framework, that was a signal I was adding it for vanity. The framework became my filter for taste.

DoD Framework Reference Eight phases: Plan → Develop → Build → Test → Release & Deliver → Deploy → Operate → Monitor. Security is woven through every phase via continuous feedback loops, not bolted on at the end. The framework mandates SIEM/SOAR integration at every phase — a requirement that directly shaped the observability stack in this build.

The principles I carried straight out of the framework and into the build:

  • Zero Trust Architecture — a perimeter is not a security model; access gets verified at every layer, every time
  • SIEM/logging integration from the first phase, not duct-taped on after something breaks
  • Runtime defense and vulnerability management treated as baseline requirements, not stretch goals
  • Infrastructure as Code so every deployment is reproducible, auditable, and reversible
  • Secrets management — no hardcoded credentials, ever, in any file, no exceptions
  • Immutable infrastructure — services get rebuilt from templates, not hand-patched in place

05 — Plan Phase — Architecture Design

The Plan phase is about thinking before typing — system design, threat modeling, configuration management, tool selection. In practice that meant I drew the entire network topology before I ran a single command. It's tempting to skip this part because it produces nothing you can show off. But every hour I spent on the whiteboard up front saved me several hours of tearing something down later. The shape of the system is the one decision that's expensive to change after the fact.

Core Design Decisions

Decision 01 — LXC Containers Over VMs

Proxmox runs both full virtual machines and LXC containers. A full VM ships its own kernel, its own OS overhead, and emulated hardware — the right tool when you need hard isolation or a different kernel. LXCs share the host kernel and lean on Linux namespaces and cgroups for separation instead. They boot in milliseconds, sip RAM, and clone from a template in seconds.

For what I needed — eight long-running Linux services living on one modest machine — LXCs were the obvious call. Each service still gets its own filesystem, process space, network interface, and user account, but without paying the full-VM tax eight times over. This also lines up neatly with the DoD's idea of "immutable infrastructure from master images": the base template is the master image, and every container is just a clone of it.

Decision 02 — Isolated Internal Network

Every LXC lives on a private Linux bridge (vmbr1, 10.10.10.0/24) that is completely walled off from the home LAN (192.168.4.0/24). The Proxmox host plays NAT gateway — containers can reach out to the internet through it, but nothing on the home network or the open internet can reach in to them directly.

Access to individual services is granted through iptables PREROUTING rules scoped exclusively to the Tailscale interface (tailscale0). The practical effect is strict: only a device authenticated to my Tailnet can touch any service at all. Someone sitting on my home WiFi — even a guest, even a compromised IoT device — cannot reach Gitea, Vault, or Grafana, because the traffic never arrives on the interface those rules listen to.

Decision 03 — Tailscale for Zero-Trust Access

I had two options for remote access: poke holes in the home router and hope IP allowlisting was enough, or build an authenticated mesh. I chose the mesh. Tailscale stands up a WireGuard-based network where every device is cryptographically identified before it can talk to anything. NAT traversal means I never forwarded a single port on the router — as far as the ISP and the home network are concerned, none of this traffic exists.

The access rules enforce least privilege by design: I get every management port; friends get 25565 and nothing else. That policy lives in Tailscale's grants JSON, version-controlled right alongside the rest of the infrastructure, so the access model is reviewable history instead of tribal knowledge in my head.

Decision 04 — Velocity Proxy as the Entry Point

I never wanted players connecting straight to a game server. Velocity sits in front as a reverse proxy: players connect to it, and it decides which backend PaperMC node to hand them to. That single layer buys me load balancing, one consistent place to handle authentication, and the ability to pull a backend out for maintenance without kicking everyone offline. The backends themselves run in offline mode and trust Velocity to have done the Mojang auth — a trust that's enforced cryptographically by a shared forwarding secret the backends check on every single connection.

Threat Model

Yes, I threat-modeled a Minecraft server, and no, I'm not embarrassed about it — the Plan phase explicitly calls for it, and the discipline is the entire point. Here are the attack surfaces I identified and what each one is mitigated by:

  • Unauthenticated access to Proxmox management (port 8006) — mitigated: reachable only over Tailscale, locked to the tailscale0 interface by iptables
  • Credential exposure via hardcoded secrets — mitigated: HashiCorp Vault KV-v2, with no credentials living in any config file or repo
  • Lateral movement between containers — mitigated: isolated vmbr1 bridge with no inter-LXC routing by default
  • Privilege escalation via service accounts — mitigated: unprivileged LXCs plus a dedicated non-root user per service
  • Friends reaching admin interfaces — mitigated: Tailscale ACL grants restrict group:friends to port 25565 only
  • Backend spoofing past Velocity — mitigated: modern forwarding secret; backends reject any connection without it
  • World corruption during failover — mitigated: the custom write-lock system, which guarantees only one node ever holds write access

06 — Develop Phase — Infrastructure as Code

The Develop phase has a simple rule that changes everything: your infrastructure configuration lives in version control, and changes go through review before they merge. So every config file in this project — Velocity's settings, PaperMC's properties, Prometheus scrape configs, the Gitea Actions workflow itself — lives in a self-hosted Gitea repository called minecraft-infra. Nothing is configured by hand on a live box and forgotten.

The payoff is that infrastructure becomes something you can read, review, and roll back. A bad change isn't a mystery I have to reconstruct from memory at 2am — it's a diff. And because it's all in Git, the CI/CD pipeline gets to inspect every change before it ever reaches a running service, which is exactly the continuous feedback loop the framework is asking for. 

minecraft-infra/
├── velocity/
│   └── velocity.toml          # Proxy config — player routing, forwarding mode
├── minecraft/
│   ├── server.properties      # Game server settings — port, gamemode, etc
│   └── paper-global.yml       # PaperMC security — Velocity forwarding secret
├── ansible/
│   └── deploy.yml             # IaC provisioning playbook
└── .gitea/workflows/
    └── validate.yml           # CI/CD pipeline — validate then deploy
Gitea Actions Runner A self-hosted gitea-runner v1.0.3 executes the pipeline on every push. The runner runs directly on the Gitea LXC (10.10.10.30) labeled debian-latest. No external CI service, no GitHub dependency — the entire pipeline is self-contained on the homelab.

The deploy stage authenticates to the Proxmox host with an SSH key stored as a Gitea Actions secret (DEPLOY_KEY) — never committed, never in the repo. From there it uses pct push to drop updated configs straight into the target container filesystems and restart the affected services. Start to finish, a git push becomes a deployed, running config change in under two minutes, and every step of it is recorded in the run history.

07 — Build Phase — Configuration & Security Validation

The Build phase calls for static analysis and dependency scanning as baseline, non-negotiable capabilities. There's no compiled code in an infrastructure repo, so I translated that requirement into the version that actually fits: automated config validation and secret scanning on every commit, before anything is allowed near production. Same spirit, right tool for the medium.

The pipeline runs four gates in order. If any gate fails, the deploy never happens — the broken change simply doesn't ship.

Gate 01 — TOML Syntax Validation

Validates velocity.toml with Python's toml library. A malformed TOML file is a genuinely nasty failure: Velocity won't start at all, and it tells you why with a parser error that means nothing to a human. I'd rather catch that on a commit, for free, than discover it when the server is supposed to be live and four people are waiting in a Discord call. 

python3 -c "
import toml, sys
try:
    toml.load('velocity/velocity.toml')
    print('velocity.toml is valid')
except Exception as e:
    print(f'ERROR: {e}')
    sys.exit(1)
"
Gate 02 — Secret Scanning

Greps every config file for patterns that look like a hardcoded password, token, or key. It deliberately ignores empty fields (like rcon.password=) and skips the .gitea/ directory so the scanner doesn't flag itself. This is the homelab-scale version of the framework's requirement for repository security tooling in the Develop phase — the same idea as a commercial secret scanner, just honest about its size. 

if grep -RniE "password=.+|secret=.+" . \
  --include="*.toml" \
  --include="*.properties" \
  --exclude-dir=".git" \
  --exclude-dir=".gitea" \
  | grep -v "password=$" \
  | grep -v "rcon.password=$"; then
  echo "WARNING: Possible hardcoded secrets found"
fi
Gate 03 — Default Credential Detection

Hard-fails the pipeline the moment it finds a known default credential — password=changeme, password=admin, password=password. It's an almost insultingly simple check, and it catches the single most common way people get owned. Simple and effective beats clever and unused.

Gate 04 — Automated Deploy

Once everything above is green, the deploy job runs on its own. It SSHes into the Proxmox host with the stored deploy key, pushes the updated configs into the right containers with pct push, and restarts only the services that changed. Every run is logged in Gitea's Actions history, so there's always a paper trail of what shipped and when. 

ssh -i ~/.ssh/deploy_key root@$PROXMOX_HOST \
  "pct push 101 /tmp/velocity.toml /opt/velocity/velocity.toml && \
   pct exec 101 -- systemctl restart velocity"

08 — Building the Core Cluster

With the architecture settled, the actual build turned into a rhythm. Every container followed the exact same recipe: clone the base template, pin a static IP on vmbr1, install the service, create a dedicated non-root user, write a systemd unit, enable and start. The same eight steps, eight times. Boring is good here — boring means reproducible, and reproducible is the whole point of the Develop and Deploy phases.

Base LXC Template

It all starts from one Debian 12 (Bookworm) container I built once and never touch casually. I updated it, installed both Java 21 and Java 25 from the Eclipse Temurin repository, added the common tooling I always reach for (curl, wget, git, nano, net-tools), and then froze it into a Proxmox template. Every other container in the cluster is a full clone of that single golden image — which means every node starts life identical, and "rebuild it" is a thirty-second operation instead of an afternoon. 

# Add Temurin repo and install both Java versions
apt install -y gnupg apt-transport-https
wget -O - https://packages.adoptium.net/artifactory/api/gpg/key/public | apt-key add -
echo "deb https://packages.adoptium.net/artifactory/deb bookworm main" \
  | tee /etc/apt/sources.list.d/adoptium.list
apt update
apt install -y temurin-21-jre temurin-25-jre

# Convert to template after setup
pct template 100

Network Isolation Setup

The isolated network is just a second bridge defined in the host's /etc/network/interfaces, paired with NAT masquerade rules. The bridge has no physical port attached to it — it's a pure software switch that only the containers plug into. The host is their default gateway and their NAT router for anything that needs to reach the outside world. 

auto vmbr1
iface vmbr1 inet static
    address 10.10.10.1/24
    bridge-ports none
    bridge-stp off
    bridge-fd 0
    post-up echo 1 > /proc/sys/net/ipv4/ip_forward
    post-up iptables -t nat -A POSTROUTING -s 10.10.10.0/24 -o vmbr0 -j MASQUERADE
    post-down iptables -t nat -D POSTROUTING -s 10.10.10.0/24 -o vmbr0 -j MASQUERADE

Service Users — No Root Services

Not one service in this cluster runs as root. Every single one gets its own dedicated non-root system user, and the systemd User= directive drops privileges before the process even starts. This is the cheapest, highest-leverage security decision in the entire build: if something does get popped, the attacker lands as minecraft or gitea with that user's narrow permissions — not as root with the keys to the host. 

[Unit]
Description=Minecraft Server
After=network.target

[Service]
User=minecraft
WorkingDirectory=/opt/minecraft
ExecStart=/usr/bin/java -Xms1G -Xmx2G -jar server.jar nogui
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target

The same shape repeats everywhere: User=velocity, User=gitea, User=vault, User=prometheus, User=loki, User=promtail. No exceptions, no "just this once."

Velocity Proxy Configuration

Velocity stands in front of both Minecraft nodes and owns player routing, load balancing, and the modern forwarding handshake. The setting everything hinges on is player-info-forwarding-mode = "modern", which switches on Velocity's cryptographic forwarding-secret handshake with the backends.

That secret is a random string that Velocity and every PaperMC backend must agree on. A backend configured for Velocity forwarding will flatly reject any connection that doesn't present the right secret — which is exactly what stops a curious friend from skipping the proxy and dialing a backend node directly.

The Hardest Part of This Whole Build The trap is that Velocity and PaperMC have to agree across three separate files, and getting any one wrong fails silently. player-info-forwarding-mode in velocity.toml must be "modern". velocity.enabled in paper-global.yml must be true. online-mode in server.properties must be false. And the forwarding secret in both files has to match character-for-character. Miss one and Velocity just drops connections with no useful error anywhere. I lost hours here. What finally fixed it wasn't the documentation — it was reading the actual source to see what the handshake expected.

09 — Deploy Phase — Running Minecraft in Containers

The Deploy phase is about how artifacts actually get out the door — provisioning, deployment, and the scanning that happens right after. My deployment model is immutable: to update a Minecraft node, I don't patch the running one, I clone the template, configure the clone, and swap it in behind Velocity. The old node hangs around as a snapshot until the new one has proven itself healthy. If the new one misbehaves, rolling back is just pointing Velocity at the old box again.

The repeatable workflow for bringing a new node online:

  • Clone the base template: pct clone 100 102 --hostname minecraft-1 --full
  • Pin a static IP on vmbr1: pct set 102 --net0 name=eth0,bridge=vmbr1,ip=10.10.10.20/24
  • Start it, then configure Java, PaperMC, and the forwarding secret
  • Create the minecraft system user and set ownership
  • Install the systemd service, enable it, start it
  • Register the node in Velocity's [servers] block and try list
  • Add it to the Prometheus scrape config
  • Install the Node Exporter and Promtail agents

iptables Port Forwarding

Because the containers sit on an isolated network, the host has to deliberately forward each exposed port from the Tailscale interface to the right container. The crucial detail is that every rule is scoped to tailscale0. Traffic arriving on any other interface — the home LAN, say — simply isn't forwarded. That one scoping decision is what keeps a device on the home WiFi from ever reaching an admin service. 

# Players (and admin) reach Velocity via Tailscale
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 25565 -j DNAT --to-destination 10.10.10.10:25565

# Admin only — Gitea source control
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 3000 -j DNAT --to-destination 10.10.10.30:3000

# Admin only — HashiCorp Vault
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 8200 -j DNAT --to-destination 10.10.10.40:8200

# Admin only — Grafana dashboards
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 3001 -j DNAT --to-destination 10.10.10.50:3000

# Admin only — Prometheus
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 9090 -j DNAT --to-destination 10.10.10.50:9090

# NAT for LXC outbound internet access
iptables -t nat -A POSTROUTING -s 10.10.10.0/24 -o vmbr0 -j MASQUERADE

10 — Failover & Write-Lock System

This is the part of the build I'm proudest of, and it's the part nobody asked for — which is probably why I enjoyed it most. Running two Minecraft nodes behind Velocity is easy. Letting them share one world without quietly destroying it is the actual engineering problem, and it's the kind of problem you only discover by trying the naive thing first.

The Problem

Minecraft writes a session.lock file into the world directory specifically to stop two server processes from writing the same world at once. Point both nodes at the same world folder and let them both write, and you don't get redundancy — you get corruption. So the real constraint is: only one node may hold write access at any moment, and there has to be a reliable way to hand that access off the instant the active node falls over.

The Solution — Shared Mount + Write-Lock Watchdog

The world data lives once, on the Proxmox host at /mnt/minecraft-world, and gets bind-mounted into both containers: 

# Mount shared world into both LXCs
pct set 102 --mp0 /mnt/minecraft-world,mp=/opt/minecraft/world
pct set 106 --mp0 /mnt/minecraft-world,mp=/opt/minecraft/world

# Ownership mapped to minecraft user UID in LXC (100999 on host)
chown -R 100999:100999 /mnt/minecraft-world
chmod -R 775 /mnt/minecraft-world

On top of the shared mount, a custom watchdog daemon runs on the host and arbitrates a single lock file (/mnt/minecraft-world/.writelock) that records which node currently owns write access. The whole failover dance moves through four clean states:

State 1 — Normal
minecraft-1 ON · minecraft-2 IDLE
Lock held by 102. minecraft-2 is stopped. Players on minecraft-1.
State 2 — Failover
minecraft-1 DEAD · minecraft-2 TURNS ON
Watchdog detects 102 is down, releases lock, starts minecraft-2, acquires lock for 106.
State 3 — Recovery
minecraft-1 TURNS ON · minecraft-2 ON
Watchdog detects 102 is back. Both briefly running. Waiting 30s for 102 to fully start.
State 4 — Handback
minecraft-1 ON · minecraft-2 IDLE
Lock returned to 102. minecraft-2 stopped. Back to normal state.
#!/bin/bash
# mc-watchdog — runs as a systemd service on the Proxmox host
LOCKFILE=/mnt/minecraft-world/.writelock

node_alive() {
  pct exec $1 -- systemctl is-active minecraft &>/dev/null
}

while true; do
  OWNER=$(cat $LOCKFILE 2>/dev/null)

  # minecraft-1 is primary and dies — start minecraft-2
  if [ "$OWNER" = "102" ] && ! node_alive 102; then
    mc-lock release 102
    pct exec 106 -- systemctl start minecraft
    sleep 30
    mc-lock acquire 106
    log "FAILOVER: minecraft-1 died — minecraft-2 acquired lock"

  # minecraft-2 active and minecraft-1 recovers — hand back
  elif [ "$OWNER" = "106" ] && node_alive 102; then
    sleep 30
    mc-lock release 106
    mc-lock acquire 102
    pct exec 106 -- systemctl stop minecraft
    log "HANDBACK: lock returned to minecraft-1 — minecraft-2 now idle"
  fi

  sleep 10
done

The watchdog itself runs as a systemd service with Restart=always, so it survives host reboots and never silently dies on me. A full failover — from minecraft-1 dropping dead to minecraft-2 being live with write access — takes roughly 30–40 seconds, most of which is just waiting for a JVM to finish booting. The handback runs about 40 seconds the other direction. It's not instant, and later I'll be honest about why that trade-off exists.

Tested and Verified The watchdog log shows three complete failover/handback cycles from live testing: 14:10:34 acquired by minecraft-1 → 14:15:09 FAILOVER to minecraft-2 → 14:21:18 HANDBACK to minecraft-1. The cycle repeats indefinitely.

11 — Test Phase — Failure & Resilience Testing

The Test phase covers acceptance testing, performance testing, and hands-on security testing. For me it meant something more fun: deliberately breaking my own work to find out whether it recovered the way I claimed it would. A failover system you've never actually triggered is just a hopeful comment in a script. So I triggered all of it.

Test 01 — Remote Access Verification

Confirmed the Proxmox web UI (100.107.12.47:8006) came up over Tailscale on T-Mobile 5G with home WiFi fully disabled. Connection established in under two seconds. There are zero port-forwarding rules on the home router, and the ISP has no visibility into any of that management traffic — it's all riding an authenticated WireGuard tunnel.

Test 02 — Cross-Continental Connectivity

The real-world test: my friend stationed in Qatar connected through Tailscale and played. No meaningful latency, no rubber-banding, no chunk-loading stalls, no timeouts. Tailscale's NAT traversal and WireGuard's lean protocol absorbed the geographic distance well enough that it felt like he was on the same couch. This was the moment the bet was effectively over.

Test 03 — Access Control Enforcement

Verified that friends could reach 25565 over Tailscale but got refused on 8006, 3000, 8200, and 9090. The ACL grants behave exactly as written — a friend pointing a browser at the Proxmox UI doesn't get a login page or even a hanging timeout, just an immediate refusal, because the door isn't open to them in the first place.

Test 04 — Systemd Service Recovery

Tested Restart=always the blunt way: kill -9 on the Minecraft Java process. Systemd noticed the exit within a second and relaunched the service; the server was back online inside ~90 seconds counting world load. Velocity's failover-on-unexpected-server-disconnect = true covered the gap.

Test 05 — Write-Lock Failover Cycle

Stopped minecraft-1 with pct exec 102 -- systemctl stop minecraft while tailing the watchdog log in real time. Within 10 seconds the watchdog saw the outage; within 40 it had started minecraft-2, transferred the lock, and put the node into service. I then restarted minecraft-1 and watched the full handback complete cleanly. Ran the whole cycle three times to make sure it wasn't luck.

Test 06 — CI/CD Pipeline Validation

Pushed a deliberately broken velocity.toml to confirm the pipeline would protect me from myself. It caught the syntax error in the validation stage and refused to deploy. Fixed it, pushed again, watched it pass every gate and auto-deploy the corrected config to the velocity-proxy container with a service restart. The guardrail works.

12 — Operate Phase — Backups & Reliability

The Operate phase is the unglamorous part — scaling, balancing, backups, and all the small decisions that decide whether a server is still up six months from now. Proxmox does a lot of the heavy lifting: snapshots give me point-in-time recovery, and because every node is just a clone of the template, rebuilding one from scratch is a five-minute job rather than a crisis.

Sleep Prevention

Here's a lesson the EliteDesk taught me the hard way: it's a business desktop, and business desktops are built to go to sleep. For a 24/7 server, that default is a silent killer — the machine just nods off and takes everyone offline. So I permanently masked every sleep and suspend target and told it to ignore the power button and lid switch entirely. 

systemctl mask sleep.target suspend.target \
  hibernate.target hybrid-sleep.target

# Ignore power button and lid switch
sed -i 's/#HandlePowerKey=poweroff/HandlePowerKey=ignore/' \
  /etc/systemd/logind.conf
systemctl restart systemd-logind

CPU Power Management

I set the powersave CPU governor so the machine sips power at idle but still scales up under load. The result is a host that draws roughly 10–15 watts when nobody's playing — less than a light bulb. On a box that never turns off, that's not a vanity stat; it's the difference between a server you forget about and an electricity bill you don't.

The Monitor phase is where the framework stops being theoretical for most homelabs and where I refused to cut corners. It calls for continuous monitoring, centralized logging, and alerting — and it points at NIST SP 800-137, which defines continuous monitoring as keeping ongoing awareness of security, vulnerabilities, and threats to support real risk decisions. The whole stack on 10.10.10.50 exists to make that real rather than aspirational.

Every container carries two agents. The thing that makes this feel genuinely production-grade is the query experience. In Grafana's Loki explorer, typing {job="velocity"} surfaces every player join, every disconnect, every routing decision, and every error as it happens. 14 — Security Considerations (SecOps Layer)

Security in this build isn't a section I bolted on at the end — it's the thread running through every previous one. But it's worth pulling the four load-bearing pieces into one place, because together they're what let me call this "production-grade" with a straight face.

Zero Trust Networking

The Tailscale policy is strict least privilege, expressed as grants-based JSON kept in version control. Two groups exist: group:admins with full access to every management port, and group:friends limited to 25565 alone. A friend on the Tailnet can play all day and never reach Proxmox, Gitea, Vault, or Grafana — knowing the IP addresses doesn't help them, because the grant simply doesn't extend to those ports. 

{
  "hosts": { "proxmox": "100.107.12.47" },
  "groups": {
    "group:admins": ["robasaldana@github"],
    "group:friends": ["friend@gmail.com"]
  },
  "grants": [
    {
      "src": ["group:admins"],
      "dst": ["proxmox"],
      "ip": ["tcp:22","tcp:8006","tcp:25565","tcp:3000","tcp:3001","tcp:8200","tcp:9090"]
    },
    {
      "src": ["group:friends"],
      "dst": ["proxmox"],
      "ip": ["tcp:25565"]
    }
  ]
}

Secrets Management with HashiCorp Vault

The Velocity forwarding secret, the RCON credentials, and anything else sensitive live in Vault's KV-v2 engine under the minecraft/ path. Not one of them sits in a config file or a repo. Vault is initialized with a single unseal key — a deliberate homelab simplification, not a production pattern — and auto-unseals after a reboot via a dedicated systemd service that reads the key and calls vault operator unseal once the Vault service is up. 

# Store secrets — never in config files
vault secrets enable -path=minecraft kv-v2
vault kv put minecraft/velocity forwarding-secret="..."
vault kv put minecraft/rcon password="..."

# Retrieve in pipeline using scoped token
SECRET=$(curl -s -H "X-Vault-Token: $VAULT_TOKEN" \
  http://10.10.10.40:8200/v1/minecraft/data/velocity \
  | python3 -c "import sys,json; \
    print(json.load(sys.stdin)['data']['data']['forwarding-secret'])")

Unprivileged Service Accounts

Every service — Minecraft, Velocity, Gitea, Vault, Prometheus, Grafana, Loki, Promtail — runs as a dedicated non-root system user created with useradd -r, with systemd's User= directive dropping privileges before the process starts. Compromise any one of them and the attacker is boxed into that user's permissions, with no path to root short of a separate privilege-escalation chain they'd have to find first.

Network Segmentation

The internal 10.10.10.0/24 network is invisible to the home LAN — the home router has no idea it exists. iptables rules on the host scope all admin-service access to the tailscale0 interface, and traffic arriving on vmbr0 from the home LAN is never forwarded to any container service. Defense in depth: even if one layer were misread, the next one still holds.

CI/CD Security Gates

The Gitea Actions pipeline is the control gate between a code change and production. No config reaches a running service without clearing validation first. The deploy key lives as an Actions secret, never in the repository, and the pipeline runs with the minimum it needs — push configs, restart services, nothing more. It can't read secrets it doesn't need or touch systems outside its job.

16 — Limitations & Reality Check

A writeup that only lists wins is marketing, not engineering. So here's what this build does not do well, and why I made peace with each trade-off in a homelab context. Naming your own gaps is part of the discipline the framework is trying to teach.

  • Single physical machine. Everything rides on one HP EliteDesk. If that hardware dies, all of it dies at once. This is a homelab, not a data center — the real enterprise answer is a Proxmox cluster across multiple nodes with Ceph shared storage, and that costs many multiples of $85. I chose to be honest about the single point of failure rather than pretend a one-box setup is highly available.
  • Backups are manual. The world lives on the shared host filesystem and snapshots exist, but I take them by hand. A scheduled job with a real retention policy is a known gap and the next thing on my list, not something I'll pretend is already done.
  • Vault unseal key on disk. Auto-unseal reads the key from a file on the host. In production that would be a cloud KMS so the key never touches local disk. For a homelab, behind Tailscale, on an access-controlled box, storing it locally is a trade-off I accept with my eyes open.
  • Failover isn't instant. The watchdog polls every 10 seconds and the full failover runs 30–40 seconds because minecraft-2 boots cold. Players see a brief disconnect in that window. Making it seamless means keeping the second node warm at all times, which doubles the memory footprint — and on 8GB, memory is the one thing I can't spend freely. Conscious choice, not an oversight.
  • 8GB caps the player count. At the current allocation, four players is the comfortable ceiling. The matching stick from the bet takes the box to 16GB, which is what actually expands the headroom — so the prize and the upgrade path happen to be the same $15.

17 — Conclusion

A $70 desktop. A late-night bet. A friend on the other side of the planet. And somehow, out the other end, a production-grade DevSecOps homelab mapped to a DoD framework, with a custom write-lock failover system and a real CI/CD pipeline holding it together.

But the Minecraft server was never really the point — it was the forcing function. The point is that building this by hand, on real hardware, under real constraints, taught me things no documentation ever could. The Velocity/PaperMC forwarding bug cost me hours precisely because no error message would tell me what was wrong; I only fixed it by reading source. The iptables duplicate-rule problem made me actually understand how PREROUTING chains get evaluated, not just copy a command. The shared-world mount forced me to learn how unprivileged LXCs map user IDs onto the host. None of that sticks when you click a button on a hosting panel. All of it sticks when you have to make it work yourself.

You don't need a cloud budget or a rack of servers to practice real DevSecOps. You need a clear methodology, the patience to read source code when the docs give up on you, and — ideally — a friend who almost bought a Hostinger plan. The infrastructure was the deliverable. The learning was the actual prize. The RAM was just a nice bonus.
