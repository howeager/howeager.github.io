DoD Framework Reference Eight phases: Plan → Develop → Build → Test → Release & Deliver → Deploy → Operate → Monitor. The framework mandates SIEM/SOAR integration at every phase.

These are the key principles that I carried into this build directly from the DOD framework:

  • Zero Trust Architecture — surface levelsecurity alone is not enough (especially with my friends), when giving access we must verify at every layer
  • SIEM/logging enabled implementing a SIEM is a must, I'm using Grafana/Loki for this project
  • Runtime defense and vulnerability management as baseline REQUIRED capabilities, in this case I am using Trivy to scan the containers for vulnerabilities
  • Infrastructure as Code for reproducible, auditable, version-controlled deployments, I am using Ansible to provision the servers
  • Secrets management — no hardcoded credentials, ever, in any file, I am using HashiCorp Vault to store the secrets
  • Immutable infrastructure — services are rebuilt from templates, not patched in place, I am using Proxmox to manage the servers

05 — Plan Phase — Architecture Design

The DoD Plan phase covers system design, threat modeling, configuration management planning, and tool selection. For this project, that meant deciding on the full network topology before writing a single line of config. Getting this right up front saved hours of rework later.

Core Design Decisions

Decision 01 — LXC Containers Over VMs

Proxmox supports both full virtual machines and LXC containers. Full VMs include a complete guest kernel, guest OS overhead, and emulated hardware, which is appropriate when you need strong isolation or a different kernel. LXC containers share the host kernel and use Linux namespaces and cgroups for isolation. They boot in milliseconds, use a fraction of the RAM, and can be cloned from a template in seconds.

For this use case (running eight persistent Linux services on one machine), LXCs are the right call. Each service gets its own filesystem, process space, network interface, and user accounts without the overhead of a full VM. This matches the DoD concept of "immutable infrastructure from master images": the base template is the master image, and every LXC is a clone.

Decision 02 — Isolated Internal Network

All LXCs live on a private Linux bridge (vmbr1, 10.10.10.0/24) completely separate from the home LAN (192.168.4.0/24). The Proxmox host acts as a NAT gateway. LXCs can reach the internet through it but cannot be reached from the LAN or internet directly.

Access to specific services is exposed via iptables PREROUTING rules scoped exclusively to the Tailscale interface (tailscale0). This means only devices authenticated to the Tailnet can reach any service. A device on the home WiFi cannot reach Gitea, Vault, or Grafana even if they know the internal IPs.

Decision 03 — Tailscale for Zero-Trust Access

Rather than opening ports on the home router and relying on IP allowlisting, Tailscale creates a WireGuard-based mesh VPN where every device is cryptographically authenticated. NAT traversal means zero port forwarding required on the home router. The ISP and home network are completely unaware of the VPN traffic.

ACL grants enforce least-privilege: I get full access to all management ports, friends get port 25565 only. This is implemented in Tailscale's policy JSON which is version-controlled alongside the rest of the infrastructure.

Decision 04 — Velocity Proxy as the Entry Point

Rather than exposing the Minecraft servers directly, Velocity acts as a reverse proxy. Players connect to Velocity which then routes them to a backend PaperMC node. This provides load balancing, centralized authentication handling, and the ability to take backend nodes offline for maintenance without disconnecting players. The backends run in offline mode while Velocity handles the Mojang authentication, enforced via a cryptographic forwarding secret that backends validate on every connection.

Threat Model

Even for a Minecraft server, threat modeling matters. The DoD Plan phase explicitly requires threat modeling as an activity. Here are the attack surfaces identified and their mitigations:

  • Credential exposure via hardcoded secrets — mitigated: HashiCorp Vault KV-v2, no credentials in any config file or repo
  • Lateral movement between LXCs — mitigated: isolated vmbr1 bridge, no inter-LXC routing by default
  • Privilege escalation via service accounts — mitigated: unprivileged LXCs, dedicated non-root users per service
  • Friend access to admin interfaces — mitigated: Tailscale ACL grants, port 25565 only for group:friends
  • Backend spoofing via Velocity — mitigated: modern forwarding secret, backends reject connections without valid secret
  • World data corruption on failover — mitigated: custom write-lock system, only one node writes at a time

06 — Develop Phase — Infrastructure as Code

The DoD Develop phase requires all infrastructure configuration to live in version control and all code to go through review before merging. Every config file in this project, Velocity proxy settings, PaperMC server properties, Prometheus scrape configs, Gitea Actions workflows, lives in a self-hosted Gitea repository called minecraft-infra.

This means infrastructure changes are tracked, reviewable, and reversible. It also means the CI/CD pipeline can validate changes before they hit production, which is exactly the "continuous build" feedback loop the DoD framework mandates. 

minecraft-infra/
├── velocity/
│   └── velocity.toml          # Proxy config — player routing, forwarding mode
├── minecraft/
│   ├── server.properties      # Game server settings — port, gamemode, etc
│   └── paper-global.yml       # PaperMC security — Velocity forwarding secret
├── ansible/
│   └── deploy.yml             # IaC provisioning playbook
└── .gitea/workflows/
    └── validate.yml           # CI/CD pipeline — validate then deploy
Gitea Actions Runner A self-hosted gitea-runner v1.0.3 executes the pipeline on every push. The runner runs directly on the Gitea LXC (10.10.10.30) labeled debian-latest. No external CI service, no GitHub dependency — the entire pipeline is self-contained on the homelab.

The deploy stage uses an SSH key stored as a Gitea Actions secret (DEPLOY_KEY) to authenticate to the Proxmox host. From there it uses pct push to deliver updated configs directly into the target LXC filesystems and restarts the affected services. The entire flow from git push to deployed config takes under two minutes.

07 — Build Phase — Configuration & Security Validation

The DoD Build phase requires Static Application Security Testing (SAST) and dependency vulnerability checking as baseline REQUIRED capabilities. For an infrastructure project with no compiled code, this translates to automated config validation and secret scanning on every commit before anything reaches production.

The pipeline runs four gates in sequence. If any gate fails, the deploy stage does not run:

Gate 01 — TOML Syntax Validation

Validates velocity.toml for syntax errors using Python's toml library. A malformed TOML file is a particularly nasty failure mode: Velocity will refuse to start entirely with a cryptic parsing error rather than a helpful message. Catching this at commit time costs zero downtime. 

python3 -c "
import toml, sys
try:
    toml.load('velocity/velocity.toml')
    print('velocity.toml is valid')
except Exception as e:
    print(f'ERROR: {e}')
    sys.exit(1)
"
Gate 02 — Secret Scanning

Scans all config files for patterns matching hardcoded passwords, tokens, and keys using grep with regex. The scanner excludes empty fields (like rcon.password=) and the .gitea/ workflows directory to avoid false positives from the scanner scanning itself. Maps directly to the DoD requirement for source code repository security plugins in the Develop phase. 

if grep -RniE "password=.+|secret=.+" . \
  --include="*.toml" \
  --include="*.properties" \
  --exclude-dir=".git" \
  --exclude-dir=".gitea" \
  | grep -v "password=$" \
  | grep -v "rcon.password=$"; then
  echo "WARNING: Possible hardcoded secrets found"
fi
Gate 03 — Default Credential Detection

Hard fails the pipeline if any config file contains known default credentials like password=changeme, password=admin, or password=password. This is a simple check but it catches the most common credential hygiene failure mode. Simple and effective.

Gate 04 — Trivy CVE Scan

Runs a Trivy filesystem scan against the entire repository on every push. Trivy checks all files, dependencies, and configs against its CVE database and fails the pipeline on any HIGH or CRITICAL severity finding that has a fix available. This maps directly to the DoD Build phase requirement for dependency vulnerability checking as a REQUIRED baseline capability. Trivy is installed directly on the Gitea runner LXC via the Aqua Security apt repo. 

trivy fs . \
  --severity HIGH,CRITICAL \
  --exit-code 1 \
  --ignore-unfixed \
  --no-progress \
  --format table \
  --skip-dirs ".git" \
  --skip-dirs ".gitea"
Gate 05 — Automated Deploy

If all four validation gates pass, the deploy job runs automatically. It SSHs into the Proxmox host using the stored deploy key, pushes updated configs into the target LXCs using pct push, and restarts the affected services. The entire process is logged in the Gitea Actions run history for auditability. 

ssh -i ~/.ssh/deploy_key root@$PROXMOX_HOST \
  "pct push 101 /tmp/velocity.toml /opt/velocity/velocity.toml && \
   pct exec 101 -- systemctl restart velocity"

08 — Building the Core Cluster

With the design locked in, the actual build followed a strictly repeatable pattern for every LXC: clone base template → set static IP on vmbr1 → install service → create dedicated non-root system user → configure systemd unit → enable and start. The same pattern, eight times.

Base LXC Template

A Debian 12 (Bookworm) LXC was created from the Proxmox template repository, updated, and configured with both Java 21 and Java 25 pre-installed via the Eclipse Temurin repository. Common tooling (curl, wget, git, nano, net-tools) was installed. The LXC was then converted to a Proxmox template. Every subsequent LXC in the cluster is a full clone of this template, consistent, reproducible, and fast to spin up. 

# Add Temurin repo and install both Java versions
apt install -y gnupg apt-transport-https
wget -O - https://packages.adoptium.net/artifactory/api/gpg/key/public | apt-key add -
echo "deb https://packages.adoptium.net/artifactory/deb bookworm main" \
  | tee /etc/apt/sources.list.d/adoptium.list
apt update
apt install -y temurin-21-jre temurin-25-jre

# Convert to template after setup
pct template 100

Network Isolation Setup

A second bridge interface was added to the Proxmox host's /etc/network/interfaces with NAT masquerade rules. The bridge has no physical ports; it's a pure software switch that only the LXCs connect to. The host acts as the default gateway and NAT router for all LXC internet traffic. 

auto vmbr1
iface vmbr1 inet static
    address 10.10.10.1/24
    bridge-ports none
    bridge-stp off
    bridge-fd 0
    post-up echo 1 > /proc/sys/net/ipv4/ip_forward
    post-up iptables -t nat -A POSTROUTING -s 10.10.10.0/24 -o vmbr0 -j MASQUERADE
    post-down iptables -t nat -D POSTROUTING -s 10.10.10.0/24 -o vmbr0 -j MASQUERADE

Service Users — No Root Services

Every service in the cluster runs as a dedicated non-root system user. The systemd unit files use the User= directive to drop privileges before execution. If a service is compromised, the attacker's blast radius is limited to that user's permissions, with no path to root without a privilege escalation chain. 

[Unit]
Description=Minecraft Server
After=network.target

[Service]
User=minecraft
WorkingDirectory=/opt/minecraft
ExecStart=/usr/bin/java -Xms1G -Xmx2G -jar server.jar nogui
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target

The same pattern applies to every service: User=velocity, User=gitea, User=vault, User=prometheus, User=loki, User=promtail. No service runs as root.

Velocity Proxy Configuration

Velocity sits in front of both Minecraft nodes and handles player routing, load balancing, and the modern forwarding protocol. The critical configuration is player-info-forwarding-mode = "modern", which enables Velocity's cryptographic forwarding secret handshake with the backends.

The forwarding secret is a randomly generated string that both Velocity and each PaperMC backend must share. Backends configured with Velocity forwarding will reject any connection that doesn't present the correct secret, preventing players from bypassing the proxy and connecting directly to the backend.

The Hardest Part of This Build The interdependencies between Velocity and PaperMC are not obvious. The player-info-forwarding-mode in velocity.toml must be labeled as "modern". The velocity.enabled setting in the paper-global.yml must be true. The online-mode in server.properties must be false in contrary. The forwarding secret in both files must of these wrong causes Velocity to silently drop connections with no useful error to match exactly.

09 — Deploy Phase — Running Minecraft in Containers

The DoD Deploy phase covers artifact deployment, infrastructure provisioning, and post-deployment security scanning. The deployment model here is immutable: to update a Minecraft node, you clone the template, configure it, and swap it in behind Velocity. The old node is kept as a snapshot until the new one is confirmed healthy.

The deployment workflow for a new node:

  • Clone base template: pct clone 100 102 --hostname minecraft-1 --full
  • Set static IP on vmbr1: pct set 102 --net0 name=eth0,bridge=vmbr1,ip=10.10.10.20/24
  • Start and configure Java, PaperMC, forwarding secret
  • Create minecraft system user, set ownership
  • Install systemd service, enable and start
  • Register in Velocity's [servers] block and try list
  • Add to Prometheus scrape config
  • Install Node Exporter and Promtail agents

iptables Port Forwarding

Since LXCs are on an isolated internal network, Proxmox uses iptables PREROUTING rules to forward specific ports from the Tailscale interface to the appropriate LXC. Each rule is interface-scoped to tailscale0 this means that only traffic arriving on the Tailscale interface is forwarded, any other interface is not forwarded, which is what keeps the home LAN from reaching admin services. 

# Players (and admin) reach Velocity via Tailscale
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 25565 -j DNAT --to-destination 10.10.10.10:25565

# Admin only — Gitea source control
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 3000 -j DNAT --to-destination 10.10.10.30:3000

# Admin only — HashiCorp Vault
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 8200 -j DNAT --to-destination 10.10.10.40:8200

# Admin only — Grafana dashboards
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 3001 -j DNAT --to-destination 10.10.10.50:3000

# Admin only — Prometheus
iptables -t nat -A PREROUTING -i tailscale0 -p tcp \
  --dport 9090 -j DNAT --to-destination 10.10.10.50:9090

# NAT for LXC outbound internet access
iptables -t nat -A POSTROUTING -s 10.10.10.0/24 -o vmbr0 -j MASQUERADE

10 — Failover & Write-Lock System

This is the most interesting engineering problem in the entire build. Running two Minecraft nodes behind Velocity is straightforward. Making them share the same world data without corrupting it is not.

The Problem

Minecraft uses a session.lock file in the world directory to prevent two server processes from writing to the same world simultaneously. If both nodes mount the same world folder and both try to write, you get data corruption. If only one node has write access at a time, you need a mechanism to hand off that access when the primary node fails.

The Solution — Shared Mount + Write-Lock Watchdog

The world data lives on a shared directory on the Proxmox host (/mnt/minecraft-world) mounted into both LXCs as a bind mount: 

# Mount shared world into both LXCs
pct set 102 --mp0 /mnt/minecraft-world,mp=/opt/minecraft/world
pct set 106 --mp0 /mnt/minecraft-world,mp=/opt/minecraft/world

# Ownership mapped to minecraft user UID in LXC (100999 on host)
chown -R 100999:100999 /mnt/minecraft-world
chmod -R 775 /mnt/minecraft-world

A custom watchdog daemon runs on the Proxmox host and manages a write lock file (/mnt/minecraft-world/.writelock) that determines which node has write permission at any given time.

State 1 — Normal
minecraft-1 ON · minecraft-2 IDLE
Lock held by minecraft-1. minecraft-2 is stopped.
State 2 — Failover
minecraft-1 DEAD · minecraft-2 TURNS ON
Watchdog detects minecraft-1 is down, releases lock, starts minecraft-2, acquires lock for minecraft-2.
State 3 — Recovery
minecraft-1 TURNS ON · minecraft-2 ON
Watchdog detects minecraft-1 is back on. Both are briefly running. Waits 30s for minecraft-1 to fully start.
State 4 — Handback
minecraft-1 ON · minecraft-2 IDLE
Lock returned to minecraft-1. minecraft-2 stopped. Back to normal state.
#!/bin/bash
LOCKFILE=/mnt/minecraft-world/.writelock

node_alive() {
  pct exec $1 -- systemctl is-active minecraft &>/dev/null
}

while true; do
  OWNER=$(cat $LOCKFILE 2>/dev/null)

  # if minecraft-1 dies — start minecraft-2
  if [ "$OWNER" = "102" ] && ! node_alive 102; then
    mc-lock release 102
    pct exec 106 -- systemctl start minecraft
    sleep 30
    mc-lock acquire 106
    log "FAILOVER: minecraft-1 died — minecraft-2 acquired lock"

  # minecraft-2  is active and minecraft-1 recovers then hand back key
  elif [ "$OWNER" = "106" ] && node_alive 102; then
    sleep 30
    mc-lock release 106
    mc-lock acquire 102
    pct exec 106 -- systemctl stop minecraft
    log "HANDBACK: lock returned to minecraft-1 — minecraft-2 now idle"
  fi

  sleep 10
done

The watchdog runs as a systemd service with Restart=always so it survives host reboots. The full failover cycle from minecraft-1 dying to minecraft-2 being live with write access takes approximately 30-40 seconds including the startup wait. The handback cycle from minecraft-1 recovering to reclaiming the lock takes approximately 40 seconds. So in the aspect of availabilty we are on the right track!

Tested and Verified

11 — Test Phase — Failure & Resilience Testing

The DoD Test phase includes acceptance testing, performance testing, and manual security testing including penetration testing. For this project, testing meant deliberately breaking things and confirming the system recovered exactly as designed.

Test 01 — Cross-Continental Connectivity

A friend stationed in Qatar connected to the server via Tailscale. No significant latency. Casual gameplay was smooth with no rubber-banding, timeout events, or chunk loading issues. Tailscale's NAT traversal and WireGuard's efficient protocol handled the geographic distance without issue.

Test 02 — Access Control Enforcement

Confirmed that friends could reach port 25565 via Tailscale but received connection refused on ports 8006, 3000, 8200, and 9090. The Tailscale ACL grants are working exactly as designed.

Test 03 — Systemd Service Recovery

Tested Restart=always behavior by forcibly killing the Minecraft Java process with kill -9. Systemd detected the exit within 1 second and restarted the service. The server was back online within 90 seconds including world load time. Velocity's failover-on-unexpected-server-disconnect = true setting handled the brief outage.

Test 04 — Write-Lock Failover Cycle

Stopped minecraft-1 with pct exec 102 -- systemctl stop minecraft while monitoring the watchdog log in real time. Within 10 seconds the watchdog detected the outage. Within 40 seconds minecraft-2 was started, the write lock was transferred, and the node was serving players. Restarted minecraft-1 and observed the full handback cycle completing successfully. Three full cycles were tested.

Test 05 — CI/CD Pipeline Validation

Introduced a deliberate TOML syntax error into velocity.toml by adding the @ at the top of the file and pushed it. The pipeline caught it in the validation stage and the deploy stage did not run. Once I fixed the error, pushed again, pipeline passed all gates and automatically deployed the updated config to the velocity-proxy LXC and restarted the service.

12 — Operate Phase — Backups & Reliability

The DoD Operate phase covers scaling, load balancing, and backup management. Proxmox handles recovery natively. LXC snapshots provide point-in-time recovery, and the template-based deployment model means any node can be rebuilt in under five minutes.

Sleep Prevention

The HP EliteDesk ships with aggressive power management defaults that will suspend the machine after a period of inactivity. For a server, this is catastrophic I am trying to have the best uptime. All sleep and suspend targets were permanently masked: 

systemctl mask sleep.target suspend.target \
  hibernate.target hybrid-sleep.target

# Ignore power button and lid switch
sed -i 's/#HandlePowerKey=poweroff/HandlePowerKey=ignore/' \
  /etc/systemd/logind.conf
systemctl restart systemd-logind

CPU Power Management

The powersave CPU frequency governor was applied to keep power consumption low during idle periods while allowing the CPU to scale up under load. The host idles at approximately 10–15 watts when no players are active, less than a standard light bulb. This is meaningful for a machine that runs 24/7.

14 — Security Considerations (SecOps Layer)

Zero Trust Networking

The Tailscale ACL policy implements strict least-privilege. All access is defined in a grants-based JSON policy stored in version control. Two groups are defined: group:admins with full port access to all management services, and group:friends restricted to port 25565 only. Friends added to the Tailnet can play Minecraft but cannot reach Proxmox, Gitea, Vault, or Grafana, even if they know the IP addresses. 

{
  "hosts": { "proxmox": "100.107.12.47" },
  "groups": {
    "group:admins": ["admin@gmail"],
    "group:friends": ["friend@gmail.com"]
  },
  "grants": [
    {
      "src": ["group:admins"],
      "dst": ["proxmox"],
      "ip": ["tcp:22","tcp:8006","tcp:25565","tcp:3000","tcp:3001","tcp:8200","tcp:9090"]
    },
    {
      "src": ["group:friends"],
      "dst": ["proxmox"],
      "ip": ["tcp:25565"]
    }
  ]
}

Secrets Management with HashiCorp Vault

The Velocity forwarding secret, RCON credentials, and any future API keys are stored in Vault's KV-v2 secrets engine under the minecraft/ path. No credentials exist in any config file or repository. Vault was initialized with a single unseal key (appropriate for homelab, not production) and auto-unseals on reboot via a dedicated systemd service that reads the key and calls vault operator unseal after the Vault service starts. 

# Store secrets — never in config files
vault secrets enable -path=minecraft kv-v2
vault kv put minecraft/velocity forwarding-secret="..."
vault kv put minecraft/rcon password="..."

# Retrieve in pipeline using scoped token
SECRET=$(curl -s -H "X-Vault-Token: $VAULT_TOKEN" \
  http://10.10.10.40:8200/v1/minecraft/data/velocity \
  | python3 -c "import sys,json; \
    print(json.load(sys.stdin)['data']['data']['forwarding-secret'])")

Unprivileged Service Accounts

Every service this includesMinecraft, Velocity, Gitea, Vault, Prometheus, Grafana, Loki, and Promtail each runs as a dedicated non-root system user created with useradd -r. The systemd User= directive drops privileges before the process starts. If any service is exploited, the attacker is limited to that user's permissions with no path to root without a privilege escalation chain.

Network Segmentation

The internal 10.10.10.0/24 network is invisible to the home LAN. The home router has zero knowledge of this network's existence. iptables rules on the Proxmox host scope all admin service access to the tailscale0 interface only. Traffic arriving on vmbr0 (home LAN) is not forwarded to any LXC service.

CI/CD Security Gates

The Gitea Actions pipeline acts as a control gate between code changes and production. No config change reaches a running service without passing validation. The deploy key is stored as an Actions secret, never in the repository. The pipeline runs with the minimum permissions required so that it can push configs and restart services, nothing else.

16 — Limitations & Reality Check

Here is what this setup does not do well and why those trade-offs were acceptable for a homelab context.

  • Single physical machine. Everything runs on one HP EliteDesk. If the hardware fails, everything fails simultaneously. This is a homelab, not a data center. The correct enterprise answer is a Proxmox cluster across multiple nodes with Ceph shared storage. That costs significantly more than $70. Maybe I'll do an update and expand more on this
  • No automated backups. World data lives on the shared Proxmox host filesystem. Snapshots exist but are taken manually. A scheduled backup job with retention policy is a known gap and a future improvement.
  • Vault unseal key on disk. The auto-unseal script stores the unseal key on the Proxmox host filesystem. In production, auto-unseal would use a cloud KMS (AWS KMS, Azure Key Vault) so no key is ever stored locally. For a homelab, storing the key on an access-controlled machine behind Tailscale was an acceptable trade-off.
  • Failover is not instantaneous. The write-lock watchdog polls every 10 seconds and the failover process takes 30-40 seconds including the minecraft-2 startup time. Players will experience a disconnect during this window. A faster solution would require keeping minecraft-2 warm at all times, which doubles the memory footprint and that itseld is its implementation.
  • 8GB RAM limits player count. With the current memory allocation, four players is the comfortable operating range. In the future I will expand this limit and see what I can accomplish with it.
